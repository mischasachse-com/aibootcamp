Architecture

The agent loop

TASK

A human asks

"Assess the incident and respond proportionately"

→

MODEL

Proposes tool calls

Never executes — it proposes

→

GATES

Your code decides

dispatch() executes — or denies

→

REPORT

Loop closes

Findings + actions + "what I did not do and why"

Results feed back into the next iteration — the model proposes, your code decides. Every call lands in the audit log.

04

Defense In Depth

Three gates on every write

G1

Environment flag

ENABLE_WRITE_TOOLS=true — trainer-controlled, off by default. Writes return SIMULATED until it flips.

G2

Human approval

An operator must type APPROVE interactively. Headless contexts auto-deny — a write can't sneak through unattended.

G3

Scope check

The target must resolve inside your own rg-corbit-sq<NN> — anything else is refused.

05

Accountability

Audit everything

Why

When an agent acts, "what did it do?" must be answerable from a log — not from memory.

Every tool call appends a JSON line: tool, arguments, mode (simulated / approved / denied), result.

day3/audit_log.jsonl

{ "tool": "get_incident_details", "args": {"alert_id": "INC-2026-0001"}, "mode": "read", … }
{ "tool": "block_ip_address", "args": {"ip": "198.51.100.77", …}, "mode": "simulated", … }
{ "tool": "isolate_node", "args": {"resource_name": "st…"}, "mode": "denied", … }

simulated · approved · denied — all recorded identically

Two Backends

Manual loop vs. Foundry Agent Service

Same tools, same gates — different orchestration. The stretch path is exam-relevant.

Manual backend — core

>

You own the loop: chat completions → dispatch() → append results

>

Full trace visibility — every iteration is yours

>

No extra service dependency

Foundry backend — stretch

>

--backend foundry: AgentsClient + FunctionTool/ToolSet

>

Threads, runs, state live service-side — evaluators too

>

Tool functions still execute locally — routed through dispatch(), so the audit log stays complete
